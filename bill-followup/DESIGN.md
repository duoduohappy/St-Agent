# 设计说明

## 需求理解

问题发现不等于证实错扣；提醒不等于解决；确认有问题不等于解决；关闭也不等于解决。原交易不删除、不联系商户。退款以申请确认时间计算72小时，以退款编号关联到账；重复消费以无序交易对唯一。

## 用户已确认的实现假设（不是题面原文）

1. 两层关闭：单问题关闭与自动跟进关闭分别存储。恢复暂停只能从paused到active，不能开启closed；reopen自动功能不能重开closed问题。
2. 暂停和关闭期间只保存原始事实，主动查询可展示最新事实和历史，不自动创建问题、发送或推进结论。恢复后统一按最新事实检查，不逐条补发过期提醒。
3. 明天提醒=max(当前时间+24小时，已有最早提醒时间)，不重置追加次数；日期缺时刻先澄清。
4. 确认有问题后停止未回复链；之后明确约定单独记录，每个约定执行一次，不恢复或重置原追加额度。
5. 模拟输入要求到账有稳定编号；缺失或编号冲突保留待核对，不按金额与时间猜测去重。

补充验收约束同样实现：提交后unknown持久化、不盲目重试；核对成功只记一次；关闭/发送具有并发保护的实现边界。

## 持久化结构

| 表 | 保存内容与不变量 |
|---|---|
| clock | 持久化模拟时刻或真实时间模式；不能用init清空重置 |
| users | 各用户active/paused/closed，不能被事实文字修改 |
| inputs | 每次收到的完整解析后输入、收到时间、接收/重复/补齐/待核对结果；重放也留痕 |
| facts | 规范化事实，主键(user,kind,id)，冲突标志；退款仅允许无冲突补齐缺失资料 |
| issues | 用户、问题ID、类型、关联ID、结论、依据、跟进阶段、首次/上次实际发送时刻、追加数、延期、澄清标记 |
| appointments | 确认后独立明确约定的时刻与pending/sent/cancelled/superseded |
| notices | 稳定操作ID、逻辑提醒种类和序号、queued/unknown/sent/failed/cancelled、正文快照、提交次数与时间 |
| provider | 本地模拟通道事实，按用户和操作ID记录sent/not_sent/pending；应用无法把pending当未发送 |
| history | 全局递增seq确定接受与生效顺序，各事件附用户、问题、时刻、详情 |

数据库启用WAL，所有写操作使用BEGIN IMMEDIATE；异常回滚。用户与事实编号、问题、操作都以用户共同限定查询。没有把单个内存定时器当作持久状态。

输入原始记录指解析后的完整JSON值，**不承诺保留用户输入文件中的空格、缩进或原始字节**。协作记录另使用逐行原始字节复制。

## 无序交易对

同用户、同商户ID、同整数分金额、不同交易ID、绝对时差≤600秒。对两个交易ID排序形成规范refs；问题数据库唯一约束(user,kind,refs)，外显ID为规范refs的稳定UUID。三笔逐对比较，满足则三条问题，refs明确共享的交易。不采用传递合并。

## 退款与资料质量

先持久化，检查时重算全体去重到账，不执行“收到一次就加余额”的易重复累计操作。资料完整且无冲突/待核对，才输出可信差额、逾期或全额验证结论。`trusted_received`仅指无冲突事实子集；任何待核对导致`received_total`/`remaining`为null，不能把子集之和冒充真实累计。全额到账先到，申请后补齐时记已到账结果，无过期提醒。

同编号内容相同是重放；不同为冲突，保留原值和新原始输入。到账改关联另一退款时，两边都标不可靠。缺编号不产生猜测ID。缺资料不写成0、成功或完成。冲突人工裁决目前留作缺口，不静默自动选择一方。

## 状态与提醒

问题结论：open、normal、resolved、closed。结案依据分别是user_normal_purchase、user_confirmed、verified_receipts、user_closed。确认阶段confirmed_problem保持open。已关闭问题接收新事实，结论不改；新独立交易对可建新问题。

首次实际发送不计extra。等待回复且extra<2时，上次实际发送至少24小时后才可追加。部分到账、延期、暂停、恢复均不重置extra。confirmed_problem从未回复计划中退出；显式约定使用appointments，独立种类appointment，不增加或清空extra。重复的明确延期将原未执行约定标superseded，只有最新约定有效。

主动查询snapshot不触发检查或发送。ingest批次和advance完成后触发cycle；run持续轮询。paused/closed时不执行计划或发送。恢复按当前事实计算一条当前合格提醒，下一次从实际发送时刻算起。

## 关闭与发送的明确边界

提交持久化和实际发送分开：先将queued持久化为unknown，表示尚未确认结果；实际模拟发送在第二个BEGIN IMMEDIATE事务内，再检查用户开关、问题、资料、时间和额度，并写入provider发送事实。该事务提交是**模拟发送生效点**。

关闭命令也以BEGIN IMMEDIATE修改开关/问题和历史，事务提交是**关闭被接受点**。两事务通过SQLite数据库写锁串行化，不存在“检查后解锁、再无保护发送”的空窗。

- 关闭先提交：发送事务读取关闭状态，记录取消且无发送事实。
- 发送先提交：关闭不能声称撤回已发送事实；之后核对/确认可如实补记sent。
- 已提交但未知：保留unknown，关闭不等于外部取消；主动核对只查provider，不发送。

测试14/15用两个线程、两个Engine/数据库连接和屏障控制真实交错；测试26使用真实子进程在发送提交后直接退出，重启核对。

**模拟范围限制：** provider与应用共用本地SQLite，这是本次允许的外部通道模拟。未连接真实远程系统；真实消息通道需要提供等价的取消/顺序协议，不能仅靠本地锁宣称保证。模拟pending不会在后台自行变成延迟发送，只能继续未知或由模拟器确认未发送。

## 未知结果与恢复

unknown不计为已发送，也不能当作未发送重试；它占用问题待决位置，阻止后续发送。reconcile按相同操作ID查询：sent则原子更新通知、相应次数/时刻和一条确认历史；重复查询直接返回已有sent，不再计数。not_sent才转failed；pending/无查询结果继续unknown。核对当前由用户明确执行，不自动轮询。

核对来源准确说明：`reconcile(user, operation_id)`读取本地模拟通道provider表的持久化state/sent_at，CLI只有操作ID参数，没有“成功/失败”结果参数。通道记录由dispatch时选择的模拟behavior产生；settle-not-sent是另一个明确标记为模拟器的操作，只能将pending改为not_sent。reconcile自身不写provider、不发送，但会按查询结果写应用侧通知、次数/时刻与历史。这不是银行或真实远程通道核验。

retry仅允许已核实未发送且目前规则仍允许的failed操作，以同一操作ID再入队；保留每次提交的模拟结果配置历史。发送后崩溃、未返回成功仍可从provider核对；提交后但发送前崩溃，查不到可靠结论就保持未知。

## 用户隔离与范围

可信调用上下文指定用户；外部事实不得包含user/user_id。普通外部文本不经过命令执行器，不调用eval、shell或模型，不授予权限。CLI模拟身份由本地操作者选定，没有真实登录认证；本机数据库访问者仍可直接访问文件，不声称防御该权限级别。

## 最小方案取舍

单进程规则引擎＋SQLite＋CLI，无消息队列、多服务或模型依赖。保留必要事实与历史，不引入完整事件溯源框架。当前交易匹配为用户内两两比较，适合小规模演示；生产规模应按商户/金额/时间窗口索引优化。CLI仅输出JSON，未做业务网页。时间和外部结果显式模拟，均无费用。
